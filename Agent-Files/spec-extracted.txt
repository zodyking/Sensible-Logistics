
CONTAINER TRACKER
Product Requirements and Feature Specification - Driver Operations, Container Pool, and DOT Short-Haul Timecard
Product intent
A mobile-first Nuxt and PostgreSQL application for tracking shipping containers, chassis, drivers, trips, documents, and exact yard placement. The platform combines operational history, OCR-assisted data capture, maps, and an interactive 2D location editor.

Primary users
Drivers and administrators. Drivers have the operational dashboard. Administrators have permissions and direct management pages only; there is no separate Admin Dashboard.
Core stack
Nuxt application, PostgreSQL with PostGIS, object storage, map and OCR services
Primary interface
Mobile-first responsive web application / installable PWA
Document purpose
Product blueprint for implementation in Cursor, including container operations, self-hosted OCR/maps, and FMCSA short-haul time-record compliance.
Design direction
Clean corporate visual system with strong typography, clear status colors, restrained motion, map-centric workflows, and card layouts optimized for one-handed phone use.
Avoid a generic admin-dashboard look. The main experience should feel purpose-built for trucking and container operations.
Every important action should be achievable from a phone with minimal typing, using OCR, recent values, location defaults, and quick-action buttons.

1. Product Vision
The application is a shared operational record for the physical movement and custody of shipping containers. Every container has a persistent record containing its identity, current status, current location, current chassis, active driver or trip, documents, photos, and a chronological history of every meaningful event.
The platform should answer three questions immediately: Where is the container now? Who last handled it? What happened to it over time?
Key design principle
Never overwrite operational history. Store the current state for fast display, but generate that state from an immutable event history whenever possible. Corrections should be recorded as corrections, not silent edits.

2. Primary Product Goals
Make driver pickup and drop-off recording faster than paper, text messages, or spreadsheets.
Create a reliable container record with custody, status, location, chassis, driver, timestamp, and document history.
Let users create real-world locations and convert them into reusable operational yard maps.
Show exactly where a container sits inside a yard, including its facing and orientation.
Reduce typing by extracting container and chassis numbers from camera images with OCR.
Provide authorized company users with operational visibility and correction tools without adding a separate Admin management pages or complicating the Driver workflow.
Support poor cellular coverage through an offline-tolerant PWA and queued synchronization.
Create an architecture that can later integrate with terminal systems, TMS platforms, EDI/API feeds, and telematics.

5. Core Data Records
5.1 Container Record
Container number, normalized to uppercase with spaces removed.
ISO 6346 check-digit validation when the format supports it. Warn the user when OCR or manual input fails validation.
Physical equipment size/type such as 20 ft, 40 ft, 40 ft high cube, 45 ft, reefer, tank, open top, flat rack, or custom. This is separate from the business container type classification.
Loaded or empty state.
Required container type classification: TROPICAL, ZIM, CMA, or KING OCEAN. Store this as a controlled enum used for filtering, labels, and workflow defaults. Do not confuse it with physical equipment size/type or the ISO owner prefix.
Seal number, booking number, bill of lading, customer reference, purchase order, release number, and commodity when applicable.
Current location, current yard coordinates, current chassis, current driver/movement, active-pool state, current status, and last activity time.
Last free day, empty return deadline, detention/per-diem status, appointment time, and terminal reference when known.
Special handling flags: reefer, hazmat, overweight, damaged, customs hold, urgent, do not move.
Notes, tags, attached photos, uploaded documents, and OCR evidence.
5.2 Container Event Timeline
Every pickup, drop-off, position change, chassis change, status update, document upload, OCR correction, damage report, and manual correction becomes an event. This timeline is the authoritative history of custody and movement.
5.3 Active Container Pool and Container Activation
Separate a container's permanent identity from whether it is currently active in operations. A container record is never duplicated simply because it left and later re-entered the company's active network.
The active container pool contains containers currently at a tracked company yard, customer location, other tracked location, in pickup/drop-off workflow, in driver custody/in transit, attached to a tracked chassis or truck, or otherwise still under active operational tracking.
A normalized container number must be unique within the company container registry. The database should enforce this uniqueness so two drivers cannot create duplicate records for the same container.
When a Driver starts New Pickup and enters or scans a container number, the app first searches the active pool. If an active match exists, use that existing container record and show its current location/custody before continuing.
If the active match is already attached to another Driver or has a conflicting active movement, do not create another container. Show a conflict and require resolution before a second pickup can be confirmed.
If no active match exists, search the permanent container registry. If the number exists historically but is inactive, reactivate that same record and preserve all prior history.
If the number has never existed in the company registry, create a new persistent container record and immediately add it to the active pool with a pickup-in-progress state owned by the Driver who started the pickup.
Confirm Pickup changes the container from pickup-in-progress to Driver custody / in transit and creates the authoritative pickup event. A cancelled or abandoned unconfirmed pickup removes the temporary active pickup state while retaining any permanent identity/audit information that must be kept.
A container remains in the active pool through customer drops, yard drops, chassis changes, and later empty pickups. It leaves the active pool only through an explicit final release/return action when the company no longer intends to track its current custody, while its full historical record remains searchable.
Drop-off must move the existing container between active states and locations; it must never create a second container record.
Recommended active_pool_state values: INACTIVE, PICKUP_IN_PROGRESS, DRIVER_CUSTODY, AT_LOCATION, and EXCEPTION. Chassis attachment is tracked separately and can coexist with any relevant active state.
Recommended current-state fields on containers: active_pool_state, current_driver_id, current_location_id, active_movement_id, current_chassis_id, activated_at, and released_at. These are denormalized current-state fields backed by immutable events.
The New Pickup activation point occurs as soon as the Driver confirms the scanned/manually entered container identifier on the New Pickup screen. This happens before final Confirm Pickup so other Drivers immediately see that the container is already being worked.
Starting/activating a pickup must be transactional. Lock or atomically claim the container so two Drivers starting the same container at nearly the same time cannot both receive a valid active movement.
Enforce at most one active pickup/movement claim per container. A second Driver should see who currently has the container, its active state, and where it is believed to be instead of receiving a duplicate record.
If a Driver cancels before Confirm Pickup, clear the pickup-in-progress claim. A previously inactive historical container returns to INACTIVE; a newly created identity remains in the permanent registry but is inactive unless company policy chooses to purge empty draft identities.

6. Driver Movements, Pickups, Drop-offs, and Work Records
A movement/trip connects one Driver's pickup and drop-off activity to the real container events. In the core product, Drivers create and manage their own pickups and drop-offs; no dispatcher assignment is required.
6.1 Trip Fields
Trip/work-order ID with human-readable reference.
Driver who created/owns the movement and the truck being used, when tracked.
Container and chassis, selected from the active pool or captured/activated during pickup.
Origin, destination, and optional intermediate stops.
Planned pickup time, appointment time, planned delivery time, actual timestamps.
Customer, steamship line, booking/reference numbers, load/empty state.
Status: draft, pickup in progress, picked up / in transit, drop-off in progress, dropped off, completed, cancelled, exception.
Driver notes plus optional authorized correction/review notes.
Required-document checklist and completion state.
6.2 Driver Pickup Flow
1.  Tap New Pickup or resume one of the Driver's own active movements.
2.  Confirm location using recent locations, search, or GPS suggestion.
3.  Take a container photo or enter the number. OCR finds the container number and validates the check digit, then the app resolves it against the active pool and permanent registry before proceeding.
4.  If the container is new to the active pool, activate/reuse its persistent record as defined by the Active Container Pool rules. Then take a chassis photo or manually select a known chassis.
5.  Confirm loaded/empty state, seal number, damage, and any reference fields.
6.  Capture interchange/EIR paperwork if present.
7.  Tap Confirm Pickup. Change the container to Driver custody / in transit and create pickup, custody, chassis-attach, and departure events as appropriate.
8.  If the pickup is from a modeled yard, optionally mark the old slot as empty.
6.3 Driver Drop-off Flow
1.  Open active trip and tap Arrived / Drop Off.
2.  Validate destination using location/geofence when permission exists.
3.  Choose exact yard placement on the 2D map or scan a physical slot QR code if the location supports it.
4.  Set container orientation using rotate controls or a two-finger gesture.
5.  Capture proof photo, signature, EIR, or receiving document if required.
6.  Confirm whether chassis remains attached or is detached.
7.  Complete the Driver-managed movement and update the container current state from the new events. The container remains active at the destination unless this drop-off is explicitly marked as a final release/return from the tracked network.
6.4 Exceptions
Container not found, wrong container, wrong chassis, terminal rejection, customer refusal, damaged container, seal mismatch, appointment missed, closed gate, customs/hold issue.
Driver can select an exception type and add notes/photos without losing the active movement state. The exception becomes immediately visible on authorized management pages.
Exception resolution should be logged as a separate event.

7. Location Pool and Geospatial Model
Locations are shared operational entities, not plain address strings. A location can represent a marine terminal, rail terminal, customer, warehouse, company yard, depot, repair shop, staging area, or temporary site.
7.1 Creating a New Location
1.  User enters a name and street address.
2.  Geocoder resolves the address and opens a map centered on the result.
3.  User confirms the pin and draws the operational boundary as a polygon. A simple rectangular bounding box can be offered as the fastest option.
4.  Application stores the geometry in PostGIS and derives a local coordinate system for the 2D yard editor.
5.  User can define one or more entrances/gates and named zones such as Loaded Row, Empty Row, Repair, Customer Parking, Chassis Pool.
6.  User optionally outlines buildings, roads, fences, restricted areas, and parking lanes to produce a clean schematic rather than displaying raw satellite imagery.
7.  User saves the location to the shared pool. Company policy can make new locations immediately active or require approval by an authorized Admin.
Duplicate prevention
When a user creates a location, compare normalized addresses and nearby existing location geometries. Suggest likely matches before creating a duplicate yard or customer record.

8. Interactive 2D Yard and Container Placement
This is a signature feature. The application should turn each saved location boundary into a clean top-down operational layout. The map defines the real-world perimeter, while the 2D editor provides a simplified, fast, controllable workspace for yard placement.
8.1 Yard Editor Objects

Chassis or truck markers when the location wants to visualize equipment.
Road/drive lanes, buildings, gates, fences, parking rows, slot grids, and named zones.
Text labels, arrows, one-way indicators, no-parking/restricted zones.
Optional fixed slot objects for yards that have numbered positions.
Optional stack positions for depots that stack containers vertically.
8.2 Container Placement Behavior
Drag a container to an exact position.
Rotate continuously or in configurable increments such as 15, 45, or 90 degrees.
Snap to rows, slots, lane edges, or grid when enabled, with a temporary freeform override.
Show container number directly on the object when zoom level allows.
Status/loaded state can affect icon treatment without relying only on color.
Prevent or warn about impossible overlap with fixed objects or other containers.

Allow multi-select and bulk move for yard reorganizations by authorized users.
Support pinch zoom, pan, large touch targets, undo, redo, and a Save Position action on mobile.
8.3 Real-world Coordinate Strategy
Store both a location-relative 2D coordinate and a geographic representation when possible. A normalized local coordinate system keeps the editor fast and predictable, while PostGIS geometry lets the system translate positions back to latitude/longitude for mapping and analytics.

9. Camera Capture and OCR
OCR should reduce data entry, but the user must confirm extracted values before they become authoritative. Store the original image and OCR result so corrections can be audited and models can be improved later.
9.1 Container Number OCR
Camera capture with a framing guide sized for the container identification markings.
Detect likely text regions, extract owner code, equipment category, serial digits, and check digit.
Normalize common OCR confusions such as O/0, I/1, B/8, S/5 only when validation supports the correction.
Validate against ISO 6346 check-digit rules and rank candidate results by confidence.
If confidence is low, present two or three candidates instead of silently choosing one.
Let user tap the detected number to correct individual characters.
Keep OCR confidence, engine/model version, raw text, corrected text, and source image.
9.2 Chassis Number OCR
Use a separate OCR profile because chassis markings are less standardized than container numbers.
Allow company-specific patterns/regular expressions and known chassis-provider prefixes.
Match OCR candidates against chassis already in the company database and show likely matches.
Fallback to barcode/QR scan when equipment uses machine-readable labels.
9.3 Document OCR
Capture EIR/interchange receipts, delivery orders, bills of lading, gate tickets, repair receipts, PODs, and other paperwork.
Auto-crop, deskew, improve contrast, and create a searchable text layer.
Extract useful fields such as container number, chassis number, seal, appointment, booking/reference, terminal, date/time, and signatures where feasible.
Index OCR text for global search so users can find a document even when they only remember a reference number printed on it.
Do not auto-populate critical fields from a document without showing the extracted value for confirmation.
9.4 Photo Capture Beyond OCR
Damage photos with optional markup/annotation.
Seal photo.
Container placement proof photo.
Chassis condition and tire photos.
Before/after photos for repair or transload workflows.
Automatic capture metadata: time, user, related event, location, and GPS when permission exists.

Document categories: EIR, POD, bill of lading, delivery order, gate ticket, scale ticket, damage report, repair invoice, customs document, photo, other.
Documents can belong to a container, trip, chassis, location, customer, or specific event.
Version or replacement history for corrected documents.

Download/share permissions controlled by role and company.
Retention rules and soft delete with audit trail.
Malware scanning and file type/size validation before documents become available to other users.
11. Search and Retrieval
Global search should be one of the fastest features in the application. Authorized Admin users should be able to paste any identifier and reach the right management record immediately; Drivers can search containers and locations needed for their own workflows.
Exact/fuzzy search by container number, chassis number, seal, booking, trip, truck, driver, customer, location, bill of lading, or document OCR text.
Filters by status, loaded/empty, container size, location, driver, date range, steamship line, dwell time, exception type, and missing documents.
Saved filters/views such as Containers at Yard A, Empty Returns Due Today, Loaded Containers Over 2 Days, My Active Trips.
Recent searches and recently viewed containers on mobile.
QR/barcode scanning can deep-link directly to a container, chassis, yard slot, or trip.
12. Real-time Updates
Authorized management pages update when Drivers complete pickups, drop-offs, OCR scans, or yard moves.
Use WebSocket or server-sent event infrastructure rather than constant high-frequency polling.
Yard view should show remote position changes without requiring a page refresh.
Use optimistic UI for fast mobile actions, followed by server confirmation and conflict handling.
Presence indicators can optionally show when another user is editing the same yard or trip.
13. Offline and Weak-Signal Operation
Installable PWA with cached shell, the Driver's active movements, recent pickups/drop-offs, key location layouts, and recently viewed records.
Queue pickup/drop-off events, text fields, and photos locally while offline.
Clearly show Pending Sync status and retry automatically when connectivity returns.
Use client-generated event IDs to prevent duplicates after retries.
Resolve conflicts by event timestamp/version rather than silently overwriting newer server data.
Warn users before logging out or clearing local app data when unsynced work exists.

14.2 DOT Short-Haul Timecard - Digital View
Legal basis: 49 CFR §395.1(e)(1). When the Driver satisfies the 150 air-mile short-haul conditions, the Driver is exempt from the RODS requirements in §§395.8 and 395.11, but the motor carrier must maintain an accurate and true time record.
Clock In is the authoritative time the Driver reports for duty. Do not infer report-for-duty time from the first pickup because work can begin before the first container movement.
Clock Out is the authoritative time the Driver is released from duty. The completed record calculates the total number of on-duty hours for that day.
The digital timecard must display, at minimum: work date, Driver name, time reported for duty, time released from duty, and total on-duty hours for the day.
For a Driver used for the first time or intermittently, retain the total on-duty time for the preceding 7 days as required by 49 CFR §395.1(e)(1)(iv)(D) and §395.8(j)(2). The system should store the preceding-day totals for every Driver so the required value is always available.
The motor carrier must retain these accurate and true time records for at least 6 months. The application must prevent normal deletion of timecards inside the mandatory retention period.
The Driver Home screen must show current duty state, Clock In/Clock Out, elapsed duty window, today's on-duty total, and a Timecard button that opens the complete digital record.
Optional off-duty breaks may be recorded only when the Driver is actually relieved of duty. Such intervals reduce total on-duty time. The app must not create a mandatory 30-minute break rule for Drivers qualifying under §395.1(e)(1).
14.3 Short-Haul Qualification and HOS Guardrails
The application must treat the timecard record and short-haul qualification as related but separate concepts. A valid time record does not by itself prove compliance with every HOS driving limit.
To use §395.1(e)(1), the Driver must operate within a 150 air-mile radius of the normal work reporting location, return to that work reporting location, and be released from work within 14 consecutive hours.
For property-carrying CMV operation, at least 10 consecutive hours off duty must separate duty periods. The app can calculate this from the previous release time and the next report-for-duty time when all on-duty work is captured.
The normal 11-hour driving limit in 49 CFR §395.3(a)(3)(i) still applies. The short-haul timecard does not become an ELD and must not claim to prove 11-hour driving compliance unless actual driving time is separately measured by a compliant source.
The 60-hour/7-day or 70-hour/8-day limits in 49 CFR §395.3(b) still apply. Add a company setting for the applicable cycle and calculate rolling on-duty hours from the stored daily timecards. A 34-hour qualifying off-duty period may reset the cycle under §395.3(c).
For radius checks, calculate straight-line geodesic distance from the assigned normal work reporting location. Do not use road mileage. 150 air miles equals approximately 172.6 statute miles.
If the app only knows pickup/drop-off locations, label the radius check as based on recorded locations only. Do not display a false full-compliance badge because the route between stops is unknown.
If a Driver exceeds the short-haul conditions or it becomes apparent the Driver cannot satisfy them, immediately show: SHORT-HAUL EXCEPTION NOT AVAILABLE FOR THIS DAY. The timecard alone is no longer sufficient for that day.
If RODS are required on no more than 8 days in any rolling 30-day period, the ELD exception in 49 CFR §395.8(a)(1)(ii)(A)(1) may allow manual/paper RODS. If RODS are required more frequently, the application must not represent itself as an ELD unless it is separately built and registered to meet the ELD requirements.
14.4 Roadside / Police PDF Viewer
Add a prominent Show DOT Timecard action on the Driver Timecard screen. It opens a read-only PDF viewer optimized for roadside inspection and can also print or save the same page.
The PDF must be titled "150 Air-Mile Short-Haul Time Record - 49 CFR §395.1(e)(1)" and must also state "Time record for short-haul exception - not an ELD and not a RODS graph-grid log."
The PDF is a convenience copy of the motor carrier's retained time record. The short-haul regulation does not require the Driver to carry an ELD record when the exception applies, so the application must not label roadside display as an ELD transfer.
Generate the PDF from server-stored authoritative data, not editable client-side display state. Include a unique record ID, generated timestamp, and integrity hash/verification code so the displayed copy can be matched to the stored record.
Use Mozilla PDF.js for the in-app viewer. Generate the page with self-hosted HTML/CSS plus Playwright/Chromium or another fully self-hosted PDF renderer. No paid document service is required.

14.5 Timecard Record Integrity and Corrections
Timecards are company records and must be accurate and true. Do not silently overwrite a punch, break, or total after it has been stored.
Corrections must preserve the original value, corrected value, person making the correction, correction timestamp, and reason. ADMIN is a permission role only; corrections are performed from the Driver/timecard management page, not an Admin management pages.
A completed day should be locked against ordinary Driver edits. A Driver may submit a correction request or, if company policy allows Driver correction, every change still creates an immutable correction event.
Store timestamps in UTC internally and render them in the configured normal work reporting location time zone with the time-zone abbreviation visible on the PDF.
Retain timecard records, correction events, and any documents used to support those records for no less than the federally required 6-month period. Company policy may retain them longer.

driver_timecards: id, company_id, driver_id, work_date, reporting_location_id, reported_for_duty_at, released_from_duty_at, total_on_duty_minutes, status, short_haul_status, cycle_type, created_at, completed_at.

timecard_exports: id, timecard_id or date_range, generated_at, generated_by_user_id, file_id, verification_hash.

30. OCR and Computer Vision Specification
30.1 Primary OCR Decision
Use PaddleOCR PP-OCRv6 Medium as the primary scene-text engine for photographs of shipping containers, chassis markings, seals, unit numbers and similar equipment identifiers. This OCR service should be independent from the Nuxt process and exposed through an internal API so the model can later be upgraded without changing the application workflow.
Default model tier: PP-OCRv6 Medium for server inference and highest practical accuracy.
Secondary local pass: PP-OCRv6 Medium again using alternate OpenCV preprocessing and crops. PP-OCRv6 Small may be used only on low-power deployments where latency requires it.
Production accuracy target: fine-tune the PP-OCRv6 recognition model on the project's own labeled container and chassis photographs. Use an A-Z and 0-9 focused recognition dictionary for equipment identifiers and keep the stock model available for general scene text.
Do not use a general-purpose vision-language model as the authoritative OCR reader. It can be used later for document understanding or damage-description assistance, but identifiers must come from deterministic OCR plus validation.
Initial deployment target: Dockerized Python OCR service using PaddleOCR and OpenCV. CPU operation is valid for early deployments; a locally installed GPU can accelerate inference without changing the Nuxt API.
30.2 Why PP-OCRv6 Fits Container Images
The target images are scene text rather than clean scans: painted identifiers, reflective decals, stencils, dirt, rust, shadows, glare and variable camera distance.
Container identifiers may be horizontal, vertical, split across lines or photographed at an angle.
PP-OCRv6 is explicitly designed for multi-scenario recognition and includes industrial, rotated, blurred and irregular text cases in its benchmark categories.
The OCR engine returns text regions and recognition confidence, which allows the application to rank candidate container numbers instead of trusting a single full-image string.
30.3 Container Number Recognition Pipeline
1.  Capture a high-resolution rear-camera image. Keep the original file unmodified as evidence.
2.  Normalize EXIF orientation and create a processing copy. Downscale only if needed for inference latency while preserving readable character height.
3.  Run blur, exposure and glare quality checks. If the image is unusable, ask the driver to retake it before uploading a large file.
4.  Create several local OpenCV processing variants: original-color crop, grayscale, CLAHE contrast enhancement, mild sharpening, and perspective-corrected crop. Use adaptive thresholding only as an alternate variant because it can destroy painted character edges.
5.  Detect likely text regions with PP-OCRv6 detection. Prefer regions whose character shapes, length, and layout can form an ISO 6346 identifier, but retain nearby regions in case the number is split across lines.
6.  Run PP-OCRv6 text detection across the image.
7.  Run text recognition on detected regions and adjacent regions that may form one container number.
8.  Normalize candidate text by uppercasing and removing spaces, punctuation and line breaks where appropriate.
9.  Find candidate identifiers matching the ISO container structure: three owner-code letters, one equipment-category letter and seven digits.
10.  For freight containers, strongly prefer equipment category U. Category J represents detachable container-related equipment and Z represents trailers/chassis, so those values should not be silently converted to U.
11.  Calculate and validate the ISO 6346 check digit for every candidate.
12.  Rank candidates using OCR confidence, valid structure, local ISO 6346 check-digit validity, spatial grouping, expected character positions, and matches against container records already stored in the local database.
13.  Present the highest-ranked candidate in a confirmation screen with the source crop visible.
14.  Save the original OCR output, normalized candidate, confidence, selected candidate, validation results and any user correction.
30.4 ISO 6346 Validation Rules
Container number canonical format: AAAU1234567, where the first three letters are the owner code, the fourth letter is the equipment category, the next six digits are the serial number and the final digit is the check digit.
Implement ISO 6346 structure and check-digit validation entirely locally. No external lookup is required for container-number validation.
Do not depend on a BIC API. If owner/operator names are desired, maintain an optional locally stored reference table that authorized users can import or update independently. Container acceptance must never depend on owner-code lookup.
If the check digit is invalid, do not silently accept the OCR result as authoritative. Generate correction candidates from low-confidence characters and known OCR confusions, then ask the user when ambiguity remains.
Formatting itself should resolve many OCR ambiguities. The first four positions are alphabetic while the serial and check digit positions are numeric.
30.5 Candidate Correction Logic
The OCR correction layer should be deterministic. It should not freely invent characters. Only create alternate candidates where a low-confidence character can reasonably be confused with another character and the resulting identifier fits the expected field type and check digit.
Typical visual confusions to evaluate: O/0, I/1, L/1, Z/2, S/5, G/6, B/8.
Never apply every possible substitution combinatorially. Limit substitutions to low-confidence character positions and stop once a small set of valid candidates is found.
A valid ISO check digit should substantially increase a candidate score, but the driver still confirms the result before a pickup or drop-off creates a custody event.
30.6 OCR Confidence Policy
Use application-level confidence bands rather than exposing the raw model score alone. The exact thresholds should be tuned against the project test dataset, but the initial behavior should be:
High confidence: valid format, valid check digit and strong OCR score. Auto-fill the field and require one-tap user confirmation.
Medium confidence: valid candidate but weak recognition or conflicting alternatives. Highlight uncertain characters and require explicit review.
Low confidence: invalid check digit, no candidate matching the expected structure, or poor image quality. Rerun local inference using alternate crops, rotations, perspective correction, contrast enhancement, and thresholding. If ambiguity remains, present the best candidates for manual confirmation.
Never create a new container record solely from an unconfirmed low-confidence OCR result.
30.7 Low-confidence Local Fallback
No cloud OCR fallback is permitted. The fallback pipeline remains on the application infrastructure and reruns PaddleOCR against multiple OpenCV-generated image variants. Use the same candidate-ranking and ISO validation layer to select between attempts.
Local OCR service interface example: recognizeSceneText(image), recognizeDocument(file), healthCheck(), engineVersion().
Store which local model, model version, preprocessing profile, and crop generated each OCR attempt.
Never send customer images or documents to third-party OCR services. OCR input remains on infrastructure controlled by the application operator.
30.8 Chassis Number OCR
Use the same PP-OCRv6 scene-text service for chassis photos, but use a different validation strategy because chassis identifiers are not consistently formatted across providers.
Store chassis-owner or company-specific number patterns in local configuration rather than hard-coding one global regex.
Compare OCR candidates against existing chassis in the tenant before proposing creation of a new chassis record.
Score exact known-record matches above newly recognized strings.
Allow barcode or QR scanning with a local open-source decoder such as ZXing where chassis labels include machine-readable codes.
Support a dedicated crop mode for small stamped or plated identifiers.
For equipment using an ISO 6346 Z category identifier, run ISO validation as an additional signal.
30.9 Document OCR
For EIRs, gate tickets, delivery orders, bills of lading, scale tickets and POD documents, use PaddleOCR PP-StructureV3 as the self-hosted document pipeline. It should extract layout, text, tables, reading order, and structured regions on the same controlled infrastructure as the scene OCR service.
Run document OCR asynchronously after upload. The driver should never wait on full document parsing to complete a pickup unless a required field must be extracted before confirmation.
Index extracted text for global search.
Create field-extraction rules for container number, chassis number, seal, booking, bill of lading, date, terminal, gross weight and reference numbers.
Retain page coordinates for extracted fields so the UI can highlight where a value came from.
Do not add a managed document-OCR service. Improve extraction through PP-StructureV3 configuration, local field rules, and fine-tuning against the application document dataset.

30.11 OCR Training and Evaluation Dataset
Before declaring OCR production-ready, build a private benchmark from actual operating conditions. Generic OCR benchmark numbers are not sufficient for this application.
Collect at least 500 to 1,000 representative container images before final threshold tuning.
Include day, night, rain, glare, shadows, rust, dirt, damaged paint, vertical markings, distant photos, close photos, angled images and multiple containers in one frame.
Label the true container number and the bounding region containing the identifier.
Measure full-identifier exact-match accuracy, character accuracy, detection recall, invalid-check-digit rate, false-positive rate and percentage requiring manual correction.
Track metrics by image condition so model or capture-UI improvements can target actual failure modes.
Keep a fixed holdout set so future OCR upgrades can be compared against the same images.
30.12 OCR Acceptance Targets
The primary metric is exact full container-number match after deterministic normalization, not generic character accuracy.
Target at least 98% exact-match accuracy on good-quality, clearly visible container-number photos before enabling rapid scan workflows.
Target zero silent acceptance of identifiers that fail ISO check-digit validation.
Measure the percentage of scans that require manual correction and keep this visible in operational analytics.
All OCR failures must degrade to a fast manual-entry path. OCR can accelerate the workflow but must never block operations.
31. Mapping, Geocoding and Location Geometry Specification
31.1 Geographic Map
Use MapLibre GL JS as the browser map engine.
Use OpenStreetMap-derived data with a fully self-hosted tile pipeline. Generate regional vector tiles with Planetiler using the OpenMapTiles profile, output PMTiles archives, and render them in MapLibre GL JS.
Do not use the community tile.openstreetmap.org servers as the production backend. Host the generated PMTiles files on the application infrastructure and serve them directly to MapLibre.
Always display required OpenStreetMap attribution.
31.2 Geocoding
Use a self-hosted Nominatim instance for address search, geocoding, and reverse geocoding. Import only the required operating region initially to reduce disk and memory requirements.
Do not implement production address autocomplete against the public nominatim.openstreetmap.org API. Its public policy prohibits client-side autocomplete and limits heavy use.
Cache normalized geocoding results for saved business locations.
After geocoding, the user must visually confirm the map result before drawing a facility polygon.
31.3 Local Facility Reference Data
Do not require a paid facility-data API. Maintain terminal, rail ramp, depot, company-yard, and customer records in the local location pool. Authorized users can import approved facility datasets into local tables when useful.
When creating a terminal or depot, search the local location pool and normalized-address index before allowing a duplicate record.
If imported local reference data includes a polygon or geofence, show it as a suggested boundary that an authorized user can accept or modify.
Keep any imported facility identifiers as optional external references rather than replacing the application primary location ID.
31.4 PostGIS Responsibilities
The browser map is a visualization/editor. PostGIS is the authoritative geospatial layer.
Store facility boundary as Polygon or MultiPolygon with SRID 4326.
Store gates and significant positions as Point geometries.
Use ST_Contains/ST_Covers for location membership checks and appropriate distance functions for proximity suggestions.
Store reported GPS accuracy with every location observation used as evidence.
Never infer a container movement only from GPS. The GPS result can verify or suggest an operational event.
32. 2D Yard Renderer Specification
32.1 Rendering Library
Use Konva with vue-konva for the interactive yard layout and operational placement view. This is separate from MapLibre. MapLibre handles Earth coordinates; Konva handles the simplified local yard coordinate system.
One static background layer for roads, buildings, fences and labels.
One equipment layer for containers, chassis and active operational objects.
One selection/interaction layer for handles, drag previews, guides and temporary UI.
Disable event listening on non-interactive background shapes for performance.
Move the actively dragged object to a dedicated interaction layer when needed to reduce redraw cost.
32.2 Yard Coordinate System
Each yard layout uses normalized local coordinates independent of screen pixels.
Persist object x, y, width, height and rotation in yard coordinate units, not CSS pixels.
Store a transform between the geospatial boundary and the local yard plane so future satellite/map alignment remains possible.
Container dimensions should reflect actual nominal length ratios, such as 20 ft versus 40 ft, so the visual map remains intuitive.
32.3 Interaction Rules
Single tap selects a container. Drag moves it. Rotation uses a visible rotate handle plus optional 15-degree snapping.
Pinch zoom and two-finger pan must not accidentally move a selected container.
Provide snap-to-slot, snap-to-row and free-placement modes.
Show collision warnings when container rectangles overlap unless the location explicitly supports stacking.
Do not reject every overlap automatically because a stack can be valid. A stack-aware location uses stack level and slot capacity rules.
Save placement only after drag/rotation end rather than on every pointer movement.
Use optimistic visual updates but reconcile with the server version and show conflicts when two users move the same container concurrently.
33. Realtime, Offline and Job Processing Decisions
33.1 Realtime
Use WebSockets for live event distribution to authorized management pages, Driver screens that need shared state, and yard views.
All authoritative commands still use authenticated HTTP API endpoints. WebSockets are not the only way to perform writes.
Publish compact domain events such as container.updated, container.moved, trip.status_changed, document.ready and exception.created.
Include record ID, tenant ID, event version and server timestamp in realtime messages.
Clients receiving a version gap should re-fetch the record rather than assuming every WebSocket message arrived.
33.2 Offline Queue
Use IndexedDB through Dexie.js for cached active-trip data, location layouts, pending operational mutations, and upload metadata.
Generate the event UUID on the client before sending a pickup/drop-off mutation. The same UUID is reused on retries.
Server endpoints must enforce idempotency so reconnection never creates duplicate operational events.
Documents/photos can upload after the core event when connectivity is weak. Link them using stable client-generated IDs.
Show sync status clearly: saved locally, uploading, synced, conflict, failed.
33.3 Background Jobs
OCR, document parsing, thumbnails, notification delivery, imports and analytics should run outside the request/response path.
Use pg-boss as the durable background-job queue so jobs remain in PostgreSQL and no separate paid queue or Redis service is required for the initial deployment.
Every job must be retry-safe and keyed to the tenant and source record.
34. Cursor Implementation Constraints for OCR
Cursor should follow these implementation constraints when building the scan workflow:
Create a local OCR engine interface before integrating model-specific inference code.
Keep OCR inference in a separate service/container, not inside Vue components or browser JavaScript.
Do not persist only the final recognized string. Store evidence, confidence and validation metadata.
Implement ISO 6346 parsing and check-digit tests before wiring camera OCR.
Write unit tests containing valid and invalid real-format examples plus confusable-character cases.
Do not create new equipment automatically when OCR nearly matches an existing record. Show the existing match first.
The user must be able to tap the recognized value and correct individual characters without retaking the photo.
A scan should return candidate values and regions, not a single magic string.
Do not implement cloud OCR fallback. All OCR retries, preprocessing, model inference, and document parsing remain local.
Log OCR latency and correction outcomes so the team can determine whether model upgrades improve the real workflow.
